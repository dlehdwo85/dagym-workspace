## 2. 바셀(Vercel)에서 안 되는 것과 따로 필요한 서버

- 바셀 함수는 이제 웹소켓 연결을 받을 수 있지만(2026-06-22 공개 베타), **연결이 함수 최대 실행 시간(기본 300초, 프로 최대 800초, 베타 1,800초)에 끊기고**, 서버끼리 메모리를 공유하지 않습니다. 영상이 다니는 **UDP 통신에 대한 지원은 문서에 없습니다.** 영상 중계 서버처럼 몇 시간씩 켜져 있으면서 수천 개 포트를 여는 프로그램은 올릴 수 없습니다.
- 바셀에 그대로 두는 것: 워크인 화면, **입장권 발급 API**(누가 어떤 권한으로 들어오는지 서명한 토큰), 영상 서버가 보내는 알림(입장·퇴장·녹화 완료) 받는 API, 회의 기록 저장(Neon).

## 5. 녹화·AI 회의록 방식

- **AI 회의록에는 영상 녹화가 필요 없음.** 참가자별 음성만 따로 저장(라이브킷 트랙 내보내기, 가벼움) → 말한 구간만 음성 인식 → 요약·결정·할 일 → 일정에 저장 → [업무로 만들기].
  - 음성 인식: 워크인이 이미 쓰는 OpenAI `gpt-4o-mini-transcribe`(공식 추정 분당 $0.003, `src/lib/ai/stt.ts`). 요약: 작은 언어 모델(gpt-5-mini 입력 100만 토큰당 $0.25)로 회의 1건 약 $0.01 수준(추정).
  - 말한 구간만 보내면 비용은 '참가자-분'이 아니라 대략 '회의 분'에 비례(5명 회의면 1/5).
- **영상 녹화**: 라이브킷 egress가 회의 화면을 크롬으로 그려 MP4로 저장 → S3 호환 저장소(AWS S3·네이버 오브젝트 스토리지 등). 회의 1개당 2~6코어, 서버 한 대가 한 번에 한 회의 → 동시에 여러 회의를 녹화하면 대기 또는 서버 추가.
- **동의·보관**: 녹화 시작 시 전원 알림·동의(팀즈 방식), 보관 기간 자동 삭제(예: 90일), 녹화는 주최자만 시작. 녹음·녹화 관련 법률(통신비밀 등)은 법률 검토 필요 — 이 문서는 법률 판단이 아님.

## 6. TURN(방화벽 통과 서버)

- 영상은 보통 UDP로 오가는데, 회사·공공기관 망은 UDP를 막고 443번(보안 웹 통로)만 여는 경우가 많음 → TURN이 443번으로 영상을 대신 실어 나름.
- 라이브킷: 내장 TURN(TLS 443 또는 5349, UDP 3478). 부하분산기를 안 쓰면 443번을 TURN에 줘야 함 → **TURN 전용 도메인·인증서** 준비. 그 외 접속용 포트: 웹소켓 7880(보안 연결 앞단 필요), TCP 7881(UDP가 막혔을 때), UDP 50000~60000 또는 7882 하나.
- 다른 엔진: coturn(BSD 계열 허용형 라이선스) 별도 서버. 우리 백엔드가 시간 제한 비밀번호를 발급.
- 비용: TURN을 영상 서버와 같은 서버(또는 같은 구역 내부망)에 두면 인터넷 전송료는 추가로 거의 안 늘어남(참가자에게 가는 양은 같음).

## 7. 월 비용 계산

### 7-1. 가정 (숫자가 바뀌면 비용도 비례해서 바뀜)
- 평균 회의 5명. 참가자는 화질 3단계 동시 송출(simulcast). 라이브킷 기본값: 720p 1.7Mbps, 360p 0.45Mbps, 180p 0.16Mbps, 음성 24~48kbps.
- 받는 사람 1명이 서버에서 내려받는 양(= 우리가 내는 전송료): 갤러리(4명 × 360p ≈ 1.8Mbps), 발표자 보기(720p 1명 + 180p 3명 ≈ 2.2Mbps), 휴대폰·카메라 끈 사람·화면 공유가 섞이는 것을 감안해 **기준 1.5Mbps**, 높게 잡으면 2.5Mbps, 낮게 0.8Mbps.

- 올려 보내는 양(참가자 → 서버)은 세 곳 모두 무료.
- 서버 크기: 고객 100곳 = 월 30만 참가자-분 ÷ (22일 × 8시간) ≈ 평균 동시 28명, 몰릴 때 4배 ≈ 115명(5명 회의 23개). 미디어수프 문서 기준 코어 1개가 약 500개 '받기 연결'을 처리 → 115명 × 8개(영상 4·음성 4) ≈ 920개 ≈ 2코어. **4코어 2대**면 한 대가 고장 나도 버팀. 내부 사용은 2코어 1대.

## 9. 주요 위험 (큰 것부터)

1. **운영 책임**: 서버 장애 = 모든 고객 회의 중단. 24시간 대응 인력·절차가 없음. 클로드 세션은 상시 감시자가 아님 → 경보(문자·앱)와 대응 순서서 먼저.
2. **체감 품질**: 줌·구글은 전 세계 서버망과 수년간 다듬은 압축·보정 기술이 있음. 서울 한 곳에서 시작하면 해외 참가자는 느릴 수 있고, 약한 휴대폰 회선에서 차이가 날 수 있음.
3. **방화벽·통신망**: UDP를 막는 회사망 → TURN(443) 필수. 일부 보안 장비는 영상 통신 자체를 막음 → 고객사별 접속 점검 안내 필요.
4. **휴대폰 제약**: 웹 화면을 앱에 넣는 방식은 백그라운드·블루투스·벨 울림·화면 공유에 한계 → 네이티브 단계가 필요하고 애플 심사 변수.
5. **비용 급증**: 전송료는 사용량에 거의 정비례(AWS GB당 $0.126). 고객이 10배면 비용도 약 10배 → 요금제별 회의 시간·인원·녹화 한도 필수.
6. **개인정보·법**: 녹화·녹취 동의, 보관·삭제, 해외 서버 경유 시 국외 이전 고지, 통신비밀 관련 — 법률 검토 필요.
7. **의존성**: 라이브킷 회사의 방향 변화(아파치 2.0이라 갈라서 계속 쓸 수는 있음), 브라우저 업데이트로 인한 오작동.
8. **보안**: 회의 링크 추측·무단 입장(긴 무작위 주소·대기실·직원 시작 조건으로 막음), 공개된 영상 포트를 노린 공격. 영상은 서버에서 풀렸다 다시 암호화되는 구조(종단간 암호화를 켜면 녹화·AI 회의록 불가).

## 10. 추천과 반대 의견

**추천**: '자체 엔진' = **우리 회의 규칙·화면·녹화·AI 회의록 + 우리가 서울에서 운영하는 라이브킷 서버**.
- 0단계 시험대는 **네이버클라우드 c2-g3 1대**(월 약 6.9만 원, 국내·한국어 지원) 또는 AWS c7g.large(약 $65). 라이브킷은 ARM 서버용도 공식 제공 → 오라클 무료 서버로 같은 시험을 병행해 비용 후보 확인.
- 고객 판매 단계는 전송료가 비용을 좌우 → 그때 사용량 실측으로 오라클(약 $83) / 네이버(약 61만 원) / AWS(약 $662) 중 결정. 서버 설정은 도커로 만들어 옮길 수 있게.
- 라이브킷 클라우드는 같은 코드로 붙일 수 있어 **비상용**으로 남겨 둠(단 일본·싱가포르 경유, 전송료 있음).
- 마케팅 문구 후보(구현·시험 뒤에만): "회의가 끝나면 할 일이 담당자 업무로 바로 들어갑니다", "외부 손님은 설치 없이 링크 하나로".

**반대 근거(이 추천이 틀릴 수 있는 이유)**
1. **줌 영상 SDK가 더 낫다**: 운영 인력 0, 품질 검증됨, 월 1만 분 무료라 내부 사용은 0원. 고객 100곳에서도 월 $1,015(137만 원) — 사람 운영 시간(월 2~4일)을 돈으로 치면 차이가 줄어듦. 단 '엔진 직접' 지시와 다르고 줌 계약에 묶임.
2. **라이브킷 클라우드로 충분하다**: 같은 코드, 서버 운영 없음, 월 $500 수준. 한국 지역이 없는 것과 전송료가 약점.
3. **미디어수프가 진짜 자체 엔진이다**: 서버 규칙까지 우리 언어(타입스크립트)로 전부 우리 코드, 특정 회사 방식에 덜 묶임. 대신 +6~10주, 녹화·확장·재연결을 우리가 책임.
4. **지트시를 통째로 쓰면 가장 빠르다**: 줌 비슷한 완성품(대기실·소회의실·투표·녹화)을 바로 얻음. 대신 무거운 구조(자바·XMPP), 화면이 워크인이 아니게 되고 녹화는 회의당 크롬 1개.
5. **안 만드는 게 맞다**: 10/20 판단(화상회의는 외부 링크로 충분)과 V30 문서(자체 개발 안 함)가 있었음. 영상은 한 번 시작하면 장애 대응 책임이 계속 생김.

**우리가 못 하는 것**: 줌 수준의 전 세계 품질, 24시간 상시 운영, 전화로 참가, 수백 명 웨비나, 종단간 암호화와 AI 회의록 동시 제공.

**대표 결정이 필요한 것**: ① 엔진 방식(라이브킷 추천 / 미디어수프 / 줌 SDK) ② 시험대 클라우드(네이버 / AWS / 오라클 병행) — 계정·결제는 대표 ③ 장애 경보를 받을 사람 ④ 녹화 기본값(꺼짐 추천)과 보관 기간(예: 90일).
