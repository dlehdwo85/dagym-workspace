# 프롬프트 B — 「점검」 기능

너는 이 저장소(WORKIN)의 시니어 풀스택 개발자다. 프롬프트 A의 범용화 규칙과 부록 1 용어 사전을 그대로 따른다.
지금부터 **「점검」 메뉴**를 추가한다. 관리자가 직원 업무(청소·시설·응대 등)가 기준대로 되었는지 확인하고, 부족한 곳을 보완 요청하고, 다시 확인하는 기능이다.

## 화면 명칭 (누구나 쓰기 편한 이름으로 통일)

| 화면·개념 | 명칭 | 쓰지 않을 표현 |
|---|---|---|
| 메뉴 | **점검** | 관리자 전용 검수, 감사, 검열 |
| 항목 카드 모음 | **점검 가이드** | 검수 매뉴얼 |
| 항목 카드 | **점검 항목** | 검수 항목 |
| 현장을 돌며 기록 | **점검하기** | 순회 검수 |
| 점검 순서 묶음 | **점검 코스** | 순회 템플릿 |
| 판정 | **양호 / 보완 필요 / 해당 없음** | 합격 / 불합격 |
| 판정 기준 | **양호 기준** | 합격 기준 |
| 사각지대 | **놓치기 쉬운 곳** | 자주 놓치는 곳(직원 지적처럼 들림) |
| 후속 조치 | **보완 요청** | 재지시, 시정 명령 |
| 조치 후 재확인 | **보완 확인** | 재검수 |
| 반복 문제 개선 | **개선 과제** | 징계, 문책 |
| 통계 | **점검 리포트** | 검수 성적 |
| 점검하는 사람 | **점검자** | 검수자 |
| 업종별 기본 묶음 | **업종 템플릿** | 기준 팩 |

- 메뉴 이름에 "관리자 전용"을 붙이지 않는다. 누가 보고 쓸 수 있는지는 **권한 설정**으로 정한다(기본값: 점검 가이드·리포트는 관리자, 양호 기준 문장과 기준 사진은 직원에게 공유 가능).
- 직원에게 가는 문구는 "무엇을, 어디를, 언제까지" 중심의 정중한 요청형으로 쓴다(지적·평가 말투 금지).

## 범위

1. 점검 가이드: 항목마다 확인 방법 · 양호 기준(문장 + 기준 사진) · 놓치기 쉬운 곳 · 보완 시 조치 · 권장 주기
2. 점검하기: 휴대폰으로 점검 코스를 따라 항목별 양호/보완 필요/해당 없음 + 사진 + 메모
3. 보완 흐름: 보완 요청 → 직원 조치 → 사진으로 보완 확인 → 종결. 같은 항목이 반복해서 보완 필요면 개선 과제(기준 보완·교육·장비 교체 검토) 생성
4. 점검 리포트: 지점·분야·항목별 양호율, 반복 항목, 보완 처리 기간, "직원 체크는 완료인데 점검은 보완 필요" 목록(외부 체크 앱 연동 시)

직원의 일상 체크리스트 실행은 이 기능의 범위가 아니다. 그것은 고객사가 쓰는 다른 앱(다짐의 경우 하이링크)이나 워크인의 다른 기능이 맡고, 「점검」은 그 결과를 **확인**하는 쪽이다.

## 원칙

1. 멀티테넌트: 모든 테이블 `tenant_id`, 모든 쿼리 테넌트 격리
2. 하드코딩 금지: 분야·공간·항목·기준·역할은 모두 데이터. 업종 단어는 템플릿 데이터에만
3. 신규 가입자에게는 **공통 기본 템플릿(부록 2)** 만 기본 설치. 업종 템플릿(부록 3)은 가입 시 업종 선택으로 추가 설치. 다짐 전용 설정(부록 4)은 다짐 테넌트에만
4. 외부 체크 앱 연동은 어댑터: `StaffCheckSource` 인터페이스 하나로 받고, 연동이 없어도 기능이 완전히 동작. 첫 어댑터는 하이링크(다짐 테넌트용)
5. AI는 초안만: AI 결과는 초안으로 저장, 관리자가 승인해야 등록. 양호/보완 판정은 사람이 한다. 사람 이름·연락처·건강정보는 마스킹 후 전송
6. 모바일 우선, 한국어 기본(문구는 키 기반으로 다국어 대비), 사진 촬영 시 압축
7. 기존 기능(자료실·메일 명함·업무관리 등)과 데이터 보존. 기존 사용자·조직·권한 모델 재사용

## 목표 데이터 모델 (개념 — 기존 스택에 맞게 조정)

- `check_categories` 점검 분야(2단계 트리, 테넌트별, 이름·아이콘·정렬 수정 가능)
- `spaces` 지점별 공간(사용자 등록), `space_types` 공간 유형(템플릿 데이터)
- `check_items` 점검 항목: 제목, 분야, 적용 공간 유형, 적용 지점(전체/일부), 확인 방법(선택지 데이터: 직접 보기·작동해 보기·기록 확인·사진 비교·참관), 방법 설명, 양호 기준, 기준 사진[], 놓치기 쉬운 곳[], 보완 시 조치(담당 역할·기본 기한·외부 업체 연락 필요 여부), 권장 주기, 기본 점검자 역할, 외부 체크 항목 연결값, 근거 메모, 직원 공유 여부, 버전, 사용 여부
- `check_item_versions` 개정 이력과 사유
- `check_courses` 점검 코스(공간 순서 + 항목 묶음)
- `check_rounds` 점검 1회(지점, 점검자, 코스, 시작·종료, 유형: 정기/표본/수시)
- `check_results` 항목별 결과(양호/보완 필요/해당 없음, 메모, 사진[], 연동 시 그날 직원 체크 기록 스냅샷)
- `follow_ups` 보완 요청(담당자 또는 담당 역할, 기한, 전달 채널, 상태: 요청됨→조치 완료→보완 확인 양호/다시 보완 필요, 조치 사진)
- `external_requests` 외부 업체·건물 관리처 연락(대상, 요청일, 회신 기한, 결과)
- `improvement_tasks` 개선 과제(같은 항목이 N회 연속 보완 필요 — N은 테넌트 설정, 기본 3)
- `industry_templates` 업종 템플릿(분야·공간 유형·항목·코스를 JSON으로 묶음, 내보내기/가져오기, 사람·지점 고유 정보 제외)
- `ai_requests`, `ai_quotas` AI 사용 기록과 월 한도

## 단계

**0단계 — 분석·설계안 보고 (여기까지 하고 멈출 것)**
저장소 구조·스택·스키마·인증·권한·파일 저장·배포를 요약하고, 위 모델을 기존 구조에 얹는 설계안(테이블, 마이그레이션 순서, API, 모바일 화면 목록), 위험 요소(권한 누락, 사진 용량·비용, AI 비용)와 질문을 `docs/check-feature-design.md`로 저장한 뒤 보고하고 멈춘다. 코드는 수정하지 않는다.

**1단계 — 점검 가이드**
- 분야·공간·항목 CRUD(모바일 작성, 기준 사진), 버전 이력, 분야·공간·지점별 보기와 검색
- 권한 설정(가이드 편집 / 점검 / 열람), 기본값은 관리자
- 가입 시 업종 선택 → 공통 기본 템플릿 + 선택 업종 템플릿 설치
- "직원 공유용 양호 기준 내보내기"(공유 표시 항목만, PDF·이미지·텍스트)
- 빈 화면 안내 문구는 공통 예시로("예: 출입구 바닥 — 먼지·물기 없음")
- 완료 기준: 신규 가입한 카페 계정에서 공통 템플릿 항목만 보이고 다짐·피트니스 용어가 하나도 보이지 않는다

**2단계 — 점검하기와 보완 흐름**
- 코스를 따라 항목을 넘기며 확인 방법·양호 기준·기준 사진·놓치기 쉬운 곳을 펼쳐 보고 판정 + 사진 + 메모
- 보완 필요 → 보완 요청 자동 생성(기본값 수정 가능) → 기한 알림 → 조치 사진 → 보완 확인
- 외부 업체·건물 관리처 연락이 필요하면 연락 기록과 회신 기한 알림
- 반복 보완 필요 → 개선 과제 자동 생성
- 코스 없이 바로 기록하는 "수시 점검"
- 완료 기준: 휴대폰만으로 한 지점 점검을 끝내고, 보완 필요 건이 보완 확인까지 닫힌다

**3단계 — 외부 체크 앱 연동 (연동 대상의 데이터 구조 확인 후 진행)**
- `StaffCheckSource` 인터페이스: `getChecks(지점, 공간, 항목 연결값, 기간)` → 체크자·시각·완료 여부·사진
- 첫 어댑터: 하이링크(다짐 테넌트). 읽기 전용 API 또는 DB 뷰 중 0단계 질문으로 결정
- 점검 항목 ↔ 외부 체크 항목 연결 화면, 점검 화면에 그날 직원 체크 기록 표시, "체크 완료 & 보완 필요" 표시
- 보완 요청을 외부 앱으로 보내는 쓰기 연동은 인터페이스만 정의

**4단계 — 리포트·AI**
AI 호출은 공급자 추상화 계층 하나로(기본 Anthropic Claude API, 모델명은 환경변수). 마스킹 → 호출 → 기록 → 초안 저장.
1. 메모 → 점검 항목 초안(최우선): 자유 메모를 항목별로 나눠 `[{title, category_id, space_type, pass_criteria, blind_spots[], follow_up_action, check_method}]` 반환. 테넌트의 실제 분야·공간 목록을 컨텍스트로 주고, 맞는 것이 없으면 `null` + 이유. 점검 항목이 아닌 지시성 메모는 `not_check_item: true`로 따로 표시
2. 업무 보고 → 양호 기준 초안
3. 보완 요청 문구(정중한 요청형, 무엇을·어디를·언제까지)
4. 월간 점검 리포트 요약 + 고객사(건물주·관리 주체 등) 보고용 문장
5. 업종 템플릿 내보내기, AI 사용량 대시보드·한도

## 공통 완료 기준
- 마이그레이션은 되돌릴 수 있게
- 권한 테스트, 테넌트 격리 테스트 통과
- 프롬프트 A의 금칙어 검사 통과(새 문구에 다짐 표현 없음)
- 모바일(375px) 주요 흐름 확인
- 단계마다 `docs/check-feature-changelog.md`에 변경·남은 이슈·다음 제안 기록 후 보고

## 수용 시나리오
1. (신규 카페 계정) 가입 → "카페" 선택 → 공통 + 카페 템플릿 설치 → 점장이 "화장실" 보완 필요 기록 → 담당 직원 보완 요청 → 조치 사진 → 보완 확인 양호
2. (신규 학원 계정) 업종 템플릿 없이 공통 템플릿만으로 "소화기·비상구" 점검 코스를 만들어 사용
3. "출입구 바닥"이 3회 연속 보완 필요 → 개선 과제 자동 생성
4. 건물 시설 문제(예: 진입로 바닥 들뜸) → 외부 연락 기록 → 회신 기한 경과 알림
5. 권한 없는 직원 계정은 점검 가이드 편집·리포트 접근 불가, 공유된 양호 기준은 볼 수 있음
6. (다짐 계정) 용어 사전으로 '지점'이 '단지'로 보이고, 하이링크 체크 기록이 점검 화면에 함께 표시
7. 부록 5의 공통 메모 / 부록 6의 다짐 메모를 붙여넣으면 AI가 점검 항목 초안과 '점검 항목 아님'을 나눠 보여준다

# 부록 1 — 용어 사전 (다짐 표현 → 공통 표현)

공통 화면에는 오른쪽 표현을 쓰고, 다짐 테넌트는 용어 사전으로 왼쪽 표현을 유지한다.

| 다짐 표현 | 공통 표현 | 비고 |
|---|---|---|
| 단지 | 지점 | 사업장 단위 |
| 입주민, 회원 | 고객 | 업종 템플릿에서 '회원'·'수강생' 등으로 바꿀 수 있음 |
| 입주자대표회의(입대의), 관리주체 | 고객사 | 보고 대상(건물주·발주처 포함) |
| 관리사무소 | 건물 관리처 | |
| 커뮤니티 시설, 커뮤니티센터 | 시설, 사업장 | |
| 위탁운영, 용역비 | 운영 계약, 계약 금액 | 정산 관련 화면에서만 |
| 트레이너, 프로, 인포, 미화, 카페 매니저 | 직원(직무) | 직무 이름은 테넌트가 정의 |
| ○○쌤, 반장님 | 이름 + 직무 | 호칭 하드코딩 금지 |
| 대표, 본부장, 팀장 | 소유자, 관리자, 현장 책임자 | 라벨 변경 가능 |
| 단톡방, 관리자방 | 메신저 채널, 관리자 채널 | 특정 메신저 전제 금지 |

# 부록 3 — 업종 템플릿 예시 (가입 시 업종 선택으로 추가 설치)

업종 템플릿에도 특정 회사명·브랜드·업체명을 넣지 않는다.

**운동시설(피트니스·필라테스)**
- 공간: 운동 공간, 스트레칭 공간, 탈의실, 사물함
- 항목: 러닝머신(1분 주행, 벨트 중앙·소음·모터 커버 먼지) / 계단식 운동기구(작동 소음, 윤활) / 웨이트 기구 조절부(의자·높이 조절이 부드러움) / 매트·바닥(부착물·파손 없음) / 운동 방법·상담 신청 안내 부착 / 수업 기록 작성 / 신규 고객 첫 안내(OT) 진행 기록

**아파트·건물 커뮤니티 시설**
- 공간: 독서실, 작은도서관, 골프연습장, 스크린 골프룸, 카페, 사우나, 안내 데스크
- 항목: 독서실 좌석·사물함 번호 고정과 이름 가림 / 도서관 책장 뒤·바닥 이물 / 골프 타석 그물·줄 상태, 그물 뒤 공 회수 / 스크린 하단 부착물 잔여 / 실내 냄새(방역 업체 분사 주기 확인) / 프로그램 개설 절차(최소 인원 → 선결제 → 개강 확정) / 고객 자격 확인 절차

**카페·음료**
- 공간: 바(제조 공간), 홀, 창고
- 항목: 재료 유통기한·폐기 기록 / 제빙기·커피머신 청소 주기 / 시간대별 판매 기록 / 홀 테이블·의자 청결
