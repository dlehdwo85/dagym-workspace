# 「점검」 기능 설계안 — 0단계 (2026-11-14, 로컬 검수)

대표가 준 「WORKIN 클로드 코드 전달 프롬프트」 프롬프트 B 의 0단계 결과입니다. **분석·설계만 했고 코드는 고치지 않았습니다.**
프롬프트 A(범용화)의 규칙과 부록 1 용어 사전을 따릅니다. 근거는 `파일:줄`로 적었고, 확인하지 못한 것은 '확인 못함'이라고 적었습니다.

## 0. 한 장 요약

- 「점검」은 **새 표 13개 + 메뉴 권한 3개 + 화면 9개**로 얹을 수 있습니다. 기존 표는 하나도 바꾸지 않는 설계입니다(다짐 화면·데이터 영향 없음).
- **보완 요청은 '업무'로 만드는 것을 추천합니다.** 담당자 지정, 기한 알림, 사진 첨부, 검토(확인) 흐름이 이미 업무에 있어 다시 만들 필요가 없고, 직원은 지금 쓰는 업무 화면에서 그대로 처리합니다.
- 프롬프트의 목표 모델을 그대로 쓰면 **이름이 겹치는 곳이 3군데** 있습니다(`spaces`, `inspection`, `tenant_id`). 아래 2절에서 이름을 바꿔 제안합니다.
- **하이링크 연동(3단계)은 지금 저장소에 길이 없습니다.** 하이링크 쪽 직원 체크 기록을 어떻게 받을지(읽기 전용 API 또는 DB 보기)는 대표 답이 필요합니다. 연동이 없어도 1·2·4단계는 완전히 동작하게 설계했습니다.
- 개발(1단계~)은 프롬프트 A 가 끝난 뒤가 맞습니다. 가입 업종 목록·조직 모델(지점 스위치)·용어 사전이 A 에서 정해지고, 점검이 그 위에 올라갑니다.

## 3. 설계안

### 3-1. 표 (모두 새 표, `tenant` 칸 + 회사 조건)

| 표 | 내용 | 주요 칸 |
|---|---|---|
| `chk_categories` | 점검 분야(2단계) | tenant, parent_id, name, icon, sort, active |
| `chk_place_types` | 공간 유형 | tenant, name, sort, from_template |
| `chk_places` | 지점별 공간 | tenant, org_unit_id, place_type_id, name, sort, active |
| `chk_items` | 점검 항목 | tenant, title, category_id, place_type_ids[], unit_scope(all/some)+org_unit_ids[], method(직접 보기·작동해 보기·기록 확인·사진 비교·참관), method_note, pass_criteria, blind_spots[], fix_action(담당 역할·기본 기한·외부 연락 필요), cycle, checker_role, external_ref, basis_note, share_staff, version, active |
| `chk_item_versions` | 개정 이력 | item_id, version, snapshot(json), reason, by, at |
| `chk_photos` | 기준 사진·결과 사진·조치 사진 | tenant, owner_kind(item/result/followup), owner_id, storage_key, size, taken_at, by |
| `chk_courses` | 점검 코스 | tenant, name, org_unit_id(없으면 공통), steps(json: 공간 유형 순서 + 항목 묶음) |
| `chk_rounds` | 점검 1회 | tenant, org_unit_id, checker_id, course_id, kind(정기/표본/수시), started_at, ended_at |
| `chk_results` | 항목별 결과 | tenant, round_id, item_id, item_version, place_id, verdict(ok/fix/na), memo, staff_check(json, 연동 시) |
| `chk_followups` | 보완 요청 | tenant, result_id, task_id(업무 연결), assignee_id 또는 role, due_at, status(요청됨→조치 완료→확인 양호/다시 보완), closed_at |
| `chk_external` | 외부 업체·건물 관리처 연락 | tenant, result_id, target, asked_at, reply_due, outcome |
| `chk_improvements` | 개선 과제 | tenant, item_id, org_unit_id, streak, task_id, status |
| `chk_ai_drafts` | AI 초안 | tenant, kind, input_hash, draft(json), status(초안/승인/버림), by |

- 회사 설정(개선 과제 기준 횟수 N, 기본 3)은 `app_settings` 의 `check:<tenant>` 한 줄(용어 사전과 같은 방식, `src/lib/termsServer.ts:9`).
- 업종 템플릿은 표가 아니라 코드 안 자료(`src/lib/check/templates/*.ts`)로 두고, 설치할 때 위 표에 행으로 넣습니다. 내보내기·가져오기는 같은 JSON 모양을 씁니다(사람·지점 정보 제외).

### 3-2. 마이그레이션 순서

번호는 착수 시점의 다음 번호를 씁니다(오늘 기준 최신 255).

1. 분야·공간 유형·공간·항목·개정 이력·사진 (1단계)
2. 코스·점검 1회·결과 (2단계)
3. 보완 요청·외부 연락·개선 과제 (2단계)
4. AI 초안 (4단계)

기존 표 변경 0건. `notifications.type` 과 `menu_*_perms.menu` 는 글자 칸이고 값 제약이 없어 마이그레이션 없이 새 값을 쓸 수 있습니다(`db/migrations/028_menu_perms.sql` 에 check 없음 확인).

### 3-3. 보완 흐름 — 업무로 만드는 안(추천)

1. 점검자가 '보완 필요'로 기록 → `chk_followups` 행 + **업무 1건** 자동 생성(제목 "○○ 보완 요청", 담당자·기한은 항목의 기본값, 사진 증빙 1장 필수).
2. 직원은 평소 쓰는 업무 화면·알림에서 조치하고 사진을 올린 뒤 [검토 요청].
3. 점검자가 사진을 보고 승인하면 '보완 확인 양호'로 닫히고, 반려하면 '다시 보완 필요'.
4. 같은 항목·같은 지점이 N회 연속 보완 필요면 개선 과제(업무 1건: 기준 보완·교육·장비 교체 검토).

- 재사용하는 것: 담당 지정(`assignees.resolveAssignee`), 기한 알림(`src/lib/jobs.ts:15-127`), 사진 증빙 수 검사(`tasks.photo_required`, `src/lib/tasks.ts:759-765`), 검토 요청·반려(`src/lib/tasks.ts:756-800`).
- 직원에게 가는 문구는 "무엇을, 어디를, 언제까지" 요청형으로 고정 틀을 둡니다(지적 말투 금지).
- 반대 근거: 점검이 잦은 회사는 업무 목록에 보완 건이 많이 쌓입니다 → 업무 목록에 '점검 보완' 거름을 두고, 점검 화면에서도 따로 모아 봅니다.

### 3-4. 권한

메뉴 권한 키 3개를 추가합니다(대표의 권한 표에 자동으로 나옴).

| 키 | 뜻 | 기본값 |
|---|---|---|
| `check_guide` | 점검 가이드 편집 | 대표·관리자: 편집 / 지점 관리자: 보기 / 직원: 없음 |
| `check_run` | 점검하기·보완 확인 | 대표·관리자·지점 관리자: 사용 / 직원: 없음 |
| `check_report` | 점검 리포트 | 대표·관리자: 보기 / 그 밖: 없음 |

- 직원은 '직원 공유' 표시가 된 양호 기준 문장·기준 사진만 봅니다(별도 읽기 화면).
- 지점 범위는 기존 조직 범위 함수(`accessibleUnitIds`)를 그대로 씁니다. 팀 격리 구성원은 조직 범위가 빈 목록이라 점검 대상이 안 보입니다 — 의도대로인지 확인이 필요합니다(위험 1).
- 메뉴 이름에 '관리자 전용'을 붙이지 않습니다. 권한이 없으면 메뉴가 안 보입니다.

### 3-6. 휴대폰 화면 목록 (375px 기준)

1. 점검 홈: 오늘 할 점검, 열린 보완 요청 수, [점검하기] [수시 점검]
2. 점검하기: 코스 순서대로 한 항목씩 — 확인 방법·양호 기준·기준 사진·놓치기 쉬운 곳을 펼쳐 보고 [양호] [보완 필요] [해당 없음] + 사진 + 메모
3. 점검 끝내기: 요약(양호 n·보완 n), 보완 요청 미리 보기(담당·기한 고치기)
4. 보완 요청 목록·상세: 조치 사진과 [양호 확인] [다시 보완]
5. 점검 가이드: 분야·공간·지점별 보기와 검색
6. 점검 항목 작성·수정: 기준 사진 찍기, 개정 사유
7. 점검 코스 만들기
8. 점검 리포트
9. (직원) 공유된 양호 기준 보기

- 하단 탭은 바꾸지 않습니다. 사이드바와 프로필 시트에 '점검'을 넣고, 홈에 '오늘 점검' 카드를 둡니다(대표 결정 2).
- 사진은 기존 방식(웹 카메라 입력 + 올리기 전 줄이기)을 씁니다. 새 앱 빌드가 필요 없습니다.

### 3-7. 용어·템플릿

- 화면 명칭은 프롬프트의 표 그대로(점검·점검 가이드·점검 항목·점검하기·점검 코스·양호/보완 필요/해당 없음·보완 요청·보완 확인·개선 과제·점검 리포트).
- '지점' 표시는 용어 사전(`termsOfUser`)에서 읽습니다. 다짐은 부록 4 대로 점검 화면에서 '단지'로 보이게 사전에 점검용 낱말을 더합니다(지금 다짐 사전에는 '지점'·'위탁운영 현장'만 있음 — 대표 결정 5).
- 공통 기본 템플릿(부록 2): 분야 8개, 공간 유형 6개, 항목 20개, 코스 1개 — 모든 회사에 설치.
- 업종 템플릿(부록 3): 운동시설, 아파트·건물 커뮤니티 시설, 카페·음료 — 가입 때 고른 업종만.
- 다짐 전용 설정(부록 4): 다짐 회사 자료로만 넣습니다(코스, 11/12 현장 체크 항목, 업체명). 코드·공통 문구에는 넣지 않습니다.
- 금칙어 검사(새 문구에 다짐 표현 없음)는 A 5단계의 검사 스크립트를 그대로 씁니다.

### 3-8. AI (4단계)

- 호출은 기존 `AiProvider.chat` + JSON 형식 출력, 모델은 환경 변수 그대로.
- 흐름: 가림 → 한도 확인(`assertCompanyAi`·`assertUserBudget`) → 호출 → `ai_usage` 기록 → `chk_ai_drafts` 에 초안 저장 → 관리자가 승인해야 항목으로 등록.
- 개인정보 가림 함수는 새로 만들어야 합니다(`src/lib/ai/mask.ts`): 회사 직원 이름 목록, 전화번호·메일 모양, 건강 관련 낱말. 양호/보완 판정은 사람이 합니다.
- 메모 → 항목 초안에는 그 회사의 실제 분야·공간 목록을 문맥으로 주고, 맞는 것이 없으면 빈 값 + 이유, 점검 항목이 아닌 지시성 메모는 따로 표시합니다.

### 3-9. 외부 체크 앱 연동 (3단계)

- 인터페이스 `StaffCheckSource.getChecks(지점, 공간, 항목 연결값, 기간)` → 체크자·시각·완료 여부·사진.
- 기본은 '연동 없음' 구현(빈 결과). 연동이 없어도 모든 화면이 동작합니다.
- 첫 구현은 하이링크(다짐 회사만). **지금 저장소에는 하이링크와 통신하는 코드가 없고, 하이링크 쪽에 직원 체크 기록이 어떤 모양으로 있는지 확인하지 못했습니다**(대표 결정 4).

## 6. 결정이 필요한 질문

1. **보완 요청을 업무로 만들까요?** 추천: 업무로(3-3). 직원이 평소 화면에서 처리하고 알림·사진·검토를 다시 만들지 않습니다.
2. **휴대폰에서 '점검' 위치**: 추천은 하단 탭 유지 + 홈 카드·프로필 시트. 점검을 자주 하는 회사는 탭이 더 편하지만 탭 5칸 중 하나를 빼야 합니다.
3. **"되돌릴 수 있는 마이그레이션"**: 저장소 규칙은 추가형만입니다. 새 표만 만들고 되돌리기 SQL 을 문서로 두는 방식으로 충분한지요?
4. **하이링크 직원 체크 기록**: 하이링크에 직원 일상 체크리스트 기록이 실제로 있습니까? 있다면 누가 접근 방법(읽기 전용 API 또는 DB 보기)을 줄 수 있습니까? 답이 없으면 3단계는 뒤로 미룹니다.
5. **다짐 화면의 낱말**: 부록 4 대로 점검 화면에서 다짐은 '지점' 대신 '단지'로 표시할까요? (지금 다짐의 다른 화면은 '지점'·'위탁운영 현장'입니다.)
6. **점검 사진 보관 기간**: 추천 1년 뒤 자동 삭제(기준 사진은 계속 보관). 저장 비용과 분쟁 대비 사이의 선택입니다.
7. **누구에게 켤까요?** 추천: 모든 회사 기본 켬(공통 기본 템플릿 설치). 요금제와 묶을지는 요금 결정이라 따로 여쭙니다.
8. **개선 과제 기준**: 같은 항목 3회 연속 보완 필요(회사별 변경 가능)로 시작해도 될까요?
9. **AI 한도**: 별도 한도 표를 만들지 않고 지금 회사 AI 한도에 포함합니다. 괜찮을까요?
10. **직원 공유**: '직원 공유' 표시 항목의 양호 기준을 직원 앱에서 볼 수 있게 할 위치 — 추천은 업무 상세(보완 요청 업무 안)와 '점검' 메뉴의 읽기 전용 화면 두 곳.
11. **진행 주체와 시점**: A 와 같이 클라우드가 만들고 로컬이 단계마다 운영에서 확인, 시작은 A 종료 뒤. 이대로 할까요?

## 7. 조사 방법과 한계

- 코드 구조는 조사 대리 1개가 읽기 전용으로 훑었고, 설계에 결정적인 사실 4가지(첨부 표 제약, `inspection` 업무 유형, down 파일 없음, 메뉴 칸 제약 없음)는 로컬이 다시 확인했습니다. 나머지 줄 번호는 조사 결과 그대로입니다.
- 확인 못함: 하이링크 쪽 시스템, 사진·AI 의 실제 비용(추정치), `followUpTask` 내부 동작.
- 0단계는 여기까지입니다. 대표가 단계 진행을 지시하기 전에는 코드를 고치지 않습니다.

## 9. 클라우드 검토 의견 반영 (2026-11-14)

설계안을 클라우드 개발 대화가 읽고 준 의견입니다. 구현은 하지 않았습니다.

- 보완 요청 = 업무(일반 유형 + 연결 표) 안은 맞음. 덧붙임: 보완 요청 업무는 **'검토 필수'로 고정**한다(담당자가 조치 뒤 바로 완료해 버리면 '보완 확인' 단계가 사라지므로).
- 점검 사진을 따로 두는 안은 맞음. **빠진 것**: 회사 저장공간 계산은 지금 업무 첨부와 자료실 파일만 더한다. 점검 사진 합계를 그 계산에 더해야 '저장공간 한도에 포함'이 실제로 된다 → 1단계 범위에 넣는다.
- 2절 8번은 406차로 바뀜: 가입 때 고른 업종의 시작 템플릿을 모두 설치하고, '외식·카페'·'학원·교습'·'시설관리·용역' 업종이 생겼다. 점검 업종 템플릿은 '운동·피트니스', '시설관리·용역'(+'건설·시설관리'), '외식·카페'에 연결한다.
- 가이드 편집·판정 변경을 감사 기록으로 남기면, 감사 기록 회사별 규칙(행위자의 회사)에 따라 그 회사 화면에만 보인다.
- 사진 자동 삭제(질문 6)는 삭제라서 대표 답을 받은 뒤에만 넣는다.
